## 从输入到机器人行为

设备录音和唤醒 → Opus 与网络协议 → 服务端 ASR、LLM、TTS → 设备播音和表情；模型可通过 MCP 调用板级工具。

## 配套关系与实现判断

小智主仓首先是设备客户端，不是一个特定外壳，也不是把完整语言模型装进 ESP32。application 协调设备状态，audio 处理收音、唤醒与播音，protocols 管传输，mcp_server 和板级工具提供设备动作入口。麦克风、音频芯片、屏幕与电源依据 boards 下的具体板卡确定。

同作者 assets-generator 把唤醒词、表情、字体和背景打包成 assets.bin。可借鉴角色资产与主固件分开升级，开发多种造型时共享语音协议和状态机，分别适配显示、动作与板卡。

README 列出的 Python、Java、两套 Go 后端均已下载。Python 仓库还含 Java 管理接口与网页，部署可从只有语音服务的最简方案到完整管理平台；Java 独立后端强调管理与对话服务拆分；两套 Go 的架构和授权不同。AnimeAIChat 的 LICENSE 加了多租户与前端标志相关条件，不能简写成标准 Apache-2.0；另一 Go 为 MIT，并有独立 ASR 子模块。

电脑 py-xiaozhi、Flutter 客户端、嵌入式 Linux、同作者 SiFli 和 QuecPython 也已留档，可用于脱离机器人测试协议。Flutter 仓库 README 同时介绍付费版本，公开快照不代表包含所有商业版本源码。Linux 仓明确不含各板 BSP；SiFli 用蓝牙 PAN，构建还需固定版本 SiFli-SDK；QuecPython 运行依赖模块固件。它们不是 ESP32 板级代码的即插即用替换。

本次官方 ESP32 快照的 idf_component.yml 要求 ESP-IDF >=6.0.1，老分支和小豆固件的要求不同。当前官方工具支持某种芯片唤醒也不代表旧 emo-dot 固件支持，必须按下载的版本和板级配置交叉核对。

## 后续开发接入建议

先用电脑客户端和一个后端跑通语音，再拿一块明确型号的音频板验证；最后将挥手、点头、行走等动作注册为有参数约束的工具。课堂多设备场景另测连接数量、音频打断和重连，作者宣传的性能数字不当作我们的验收结果。

这些为开发建议，本次没有声称完成硬件复现或跨仓兼容性验证。
