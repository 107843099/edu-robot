# 纸壳迁移与课程借鉴

**建议保留纸壳作为第一版实体原型，先迁移Tiny的交互思路，再按需求增加硬件。** 本文件是研发建议，尚未形成新的设备固件；原始纸壳V0.3包完整源码与许可缺口仍见第15项。

## 三个阶段与交付物

| 阶段 | 做什么 | 交付与验收 |
|---|---|---|
| 第一版：可靠双轴纸壳 | 纸板外观、OLED、摸头、小幅点头/摇头、校准 | 物料与接线照片；每轴独立限位；供电、重启和连续运行记录 |
| 第二阶段：任务状态搭档 | 增加统一状态表；电脑或学生平台发预设动作 | ready/listening/thinking/completed/error状态卡；假设备与真设备回执；断线测试 |
| 第三阶段：自然语言意图实验 | 电脑或边缘Linux板运行Needle/其他解析器，经验证后发动作 | 有限工具表、语料及失败记录；中文/粤语单独评估；物理执行仍在控制器 |

先使用明确按钮或固定指令，把“消息到达”与“动作完成”分开记录。AI解析尚不稳定时，课堂基础操作仍应能够独立运行，不能让网络或模型阻断校准和停止。

## 状态映射建议

| 学习情境 | 可借鉴Tiny状态 | 纸壳表达建议 |
|---|---|---|
| 等待学生或指令 | none | 呼吸/眨眼，舵机停放 |
| 阅读任务 | reading | 注视任务，低幅头部运动 |
| 计算或等待回复 | thinking | 思考表情，缓慢偏头 |
| 程序执行中 | typing | 没有双臂时用屏幕节奏或轻微头部动作 |
| 成功 | ring | 点头与完成表情；铃可换成屏幕或短音效 |
| 错误/需帮助 | error/attention | 明确错误图标与教师提示 |

不要把编程助手内部“调用Bash”机械地当成学生写代码。课程应以学生能理解的任务阶段命名，由平台适配为具体机器人动作。编程助手可能失败、取消或连续发消息，动作控制器仍须限制频率和总运动时长。

## 外观与内容创作

Tiny的桌面、电脑、灯、铃让动作具有角色含义；我们的纸壳可把同一组头部动作放进不同场景，例如阅读伙伴、实验助理或情绪角色。学生分别提交外观草图、状态故事板、屏幕表情和动作幅度，观察“同一运动、不同造型”如何改变理解。保留原创角色名字，避免把上游商标和整套造型直接当课程品牌。

将硬件参数锁定在教师层；学生编辑表情、动作顺序和持续时长，平台验证后才执行。表情尺寸、坐标原点、帧率和动作曲线都作为明确素材规范，不能把上游128×32资源直接当128×64布局。

## 课程活动与评价证据

1. 拆解一个完整状态：学生说明事件、状态、屏幕和关节变化，区分原因与反馈。
2. 比较两个动作设计：相同完成事件，一种只亮图标，一种增加点头；记录可辨认性、响应时间和运动干扰。
3. 做一次异常测试：断开主机消息或输入未知动作，观察设备如何停放和反馈，不用真实堵转制造危险。
4. 设计完成奖励：参考Brass Thumb把任务完成变为实体反馈，解释为什么奖励触发应来自已验证结果。

可评分的成果包括接线正确性、校准记录、状态逻辑、内容原创性和异常解释。记录学生独立完成了哪一步，避免只用“机器人能动”作为课程效果证据。

## 对话与意图的整合边界

YOVA可参考录音、打断、预算和后端切换；Tiny可参考表现层；Needle可参考有限工具的本地解析。三者尚无本库已验证的即插即用组合。推荐架构为“语音/输入服务→意图解析→独立验证与授权→动作适配→控制器”，老师能观察每层的输入、拒绝原因与执行结果。

[Needle机器人接入方案](<../17_Needle端侧模型/机器人接入与验证方案.md>)包含本次真实失败样例。首版不需要在ESP32-C3内塞进Needle模型；先完成[纸壳制作与验收](<../15_小纸壳机器人/第一版制作与验收清单.md>)，再决定电脑、手机或更高资源的边缘板负责解析。
