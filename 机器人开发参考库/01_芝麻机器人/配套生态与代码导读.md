## 从输入到机器人行为

电脑麦克风 → SpeechRecognition 和 Google ASR → Gemini 或本地兼容接口 → 结构化动作与回复 → HTTP → ESP32 舵机和 OLED；语音由电脑侧 TTS 输出。

## 配套关系与实现判断

芝麻应作为“机械动作与表情本体 + 同作者对话应用 + 动作编辑器 + 第三方仿真研究”一起理解。主仓库不是只会执行网页按钮；它已经提供 HTTP 边界，同作者 Companion 利用这套边界把自然语言变成动作和回复。

Companion 的 VoiceInterface 用电脑默认麦克风收音，调用 recognize_google 做识别；LocalLLMInterface 请求兼容 OpenAI 格式的 /chat/completions，GeminiInterface 走 Gemini。模型输出先检查 AVAILABLE_COMMANDS 和表情列表，再由 SesameRobotController 向 /api/command 发 JSON。回复由 pyttsx3 或 Gemini TTS 在电脑上播放，讲话时发送 talk_face 表情。GUI 和命令行都在这份配套仓库中。

这里的“本地模型”只指语言模型接口可以在局域网运行，现有 recognize_google 仍联网。源码请求主要由系统提示词和当前输入组成，未看到持续累积的对话历史，因此不能把它直接写成具有长期记忆的陪伴产品。默认角色提示词带有较强的讽刺性格，教学版需要另写。

固件端支持只更新 face，也支持 command 与 face。当前 Companion 的动作分支发送动作时传入 face=None，因此“模型选出的动作和任意表情同时发送”仍需核对或调整；讲话表情有另一条线程联动。固件用字符串查找解析 JSON，对字段格式有依赖，自己的接口应采用正式解析并统一完成、停止和异常返回。

Sesame Studio 在主仓库 software 内，用关键帧编辑姿势并导出 C++ 动作，不需寻找另一个 Studio 仓库。第三方 sesame-ml 则采用 Orange Pi、PCA9685、摄像头和 IMU 的研究参考架构，运行 MessagePack 和 WebSocket 的连续关节目标；它不是 Companion 的 HTTP 对话插件，不能直接套原始 ESP32 BOM。其 README 明确未附可自动安全用于真机的预训练策略。

主 README 所列 one-for-all 浏览器模拟器页面在本次检查返回 404，对应公开 GitHub 地址也未能获取，作为失效入口留档。已有 sesame-ml 的 MJCF、URDF、评估和网络运行代码可先研究，但不把它们视为该网页模拟器的同一实现。

## 后续开发接入建议

先用文字输入验证“挥手并回答”与纯表情请求，再打开电脑麦克风和 TTS；确认模型断网、非法动作和 STOP 的行为。机身自带麦克风、喇叭需要增加音频硬件和设备端实现，现有 Companion 可作为先期对话与动作联调原型。

这些为开发建议，本次没有声称完成硬件复现或跨仓兼容性验证。
