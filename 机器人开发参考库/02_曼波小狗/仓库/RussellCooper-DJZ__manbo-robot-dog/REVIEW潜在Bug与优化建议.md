# manbo-robot-dog 潜在 Bug 与性能优化审查报告

**审查提交：** `6170864`
**审查范围：** STM32 主控代码、ESP32/ASRPro 子项目、串口通信、超声波避障、动作控制和构建配置。
**审查方式：** 静态代码审查、调用关系核对、缓冲区与中断共享变量检查。当前沙箱没有 PlatformIO、Keil 或 ARM GCC 工具链，因此未执行目标板编译和硬件测试。

## 总结

仓库中仍有若干值得优先处理的问题。其中，**ASRPro 子项目的 `setup()`/`loop()` 重复定义、STM32 语音状态查询使用 8 字节缓冲区承载长格式化字符串、语音帧固定缓冲区可能越界**属于高优先级问题；前两项可能直接导致构建失败或运行时内存破坏。串口接收采用单字节覆盖式缓存，动作和超声波逻辑大量使用阻塞延时，则会影响响应性和可靠性，但通常需要结合硬件通信速率与产品行为确认。

## 重点问题分析

### 1. ASRPro 子项目存在重复的 Arduino 入口函数

`ASRPro_Code/src/main.cpp` 定义了空的 `setup()` 和 `loop()`，而 `ASRPro_Code/src/asr.cpp` 又定义了完整的 `setup()` 和 `loop()`。PlatformIO 会编译 `src` 目录下的两个源文件，因此这不是单纯的注释问题，而是典型的重复符号风险。

建议删除 `main.cpp` 中的两个函数定义，仅保留必要的头文件，或者把完整入口迁移到 `main.cpp` 并从 `asr.cpp` 删除入口函数。更推荐前者：`asr.cpp` 负责库实现，`main.cpp` 负责 Arduino 入口，职责更清晰。

### 2. `read[8]` 是明确的内存越界漏洞

`User/Mode.c:25` 声明 `char read[8]`，但在 `mode_happiness()`、`mode_stamina()` 和 `mode_index()` 中使用 `sprintf` 写入包含协议头、中文文本和一个或两个整数的完整字符串。即使不考虑中文编码，仅协议头和固定文字也已经远超 7 个可写字符，末尾的 `\\0` 也没有空间。

建议将缓冲区改为经过测算的固定容量，例如 `char read[128]`，并改用 `snprintf(read, sizeof read, ...)`。更稳妥的做法是让 `SYN_FrameInfo` 接受长度参数并对最大帧长进行检查，从接口层避免任何未终止字符串或超长文本进入语音发送函数。

### 3. SYN6288 语音帧缺少长度校验

`Hardware/syn6288.c` 使用 `unsigned char Frame_Info[50]`，随后把 `HZ_Length` 字节复制到 `Frame_Info[5]` 开始的位置，并在 `Frame_Info[5 + HZ_Length]` 写入校验字节。安全条件是 `HZ_Length <= 44`，但代码没有检查该条件。只要传入文本超过 44 字节，就会发生越界写。

建议在函数入口检查空指针和长度，并将最大文本长度定义为常量。超长时应截断并记录错误，或者直接返回失败；不要仅依赖 `u8` 长度类型，因为它无法解决目标数组容量不足的问题。

### 4. 串口驱动会丢失连续输入，并缺少 `volatile`

USART 中断每收到一个字节就覆盖全局 `RxData` 并将 `RxFlag` 置 1。主循环读取速度受到 OLED 刷新、动作延时、语音播放和避障测距影响，连续到达的多个字节可能在主循环处理前互相覆盖。与此同时，这些被 ISR 修改的变量没有声明为 `volatile`，优化编译时主循环不一定每次都从内存重新读取。

建议至少将共享变量声明为 `volatile`，并将单字节缓存升级为环形缓冲区或带长度的事件队列。读取接口应提供“取出一个字节”的原子操作，而不是分别读取 flag 和 data。对于语音命令这种低带宽场景，8 或 16 字节环形队列通常已经足够。

### 5. 阻塞动作会放大队列和响应问题

ASR 运动命令在 `ASR_SendCommandWithDelay()` 中发送后直接阻塞 6 秒，再发送停止命令。STM32 侧的动作函数也大量使用 `Delay_ms()`，避障测距固定等待 100 ms，状态播报还会等待 4–10 秒。这些设计会使系统在动作期间无法及时消费新命令。

建议改成基于 `millis()` 或硬件定时器的非阻塞状态机：发送动作后记录截止时间，在主循环中周期性检查是否到期，再发送停止命令。STM32 的动作也可拆成小步进更新，每次循环只推进一小段角度，使串口、传感器和急停逻辑保持可响应。

### 6. 超声波避障需要超时和失效保护

`UltrasonicWave_Getvalue()` 启动测量后固定等待 100 ms，并直接使用 `Time` 计算距离。`Bizhang()` 在距离小于 15 时反复转向和测距，但没有最大重试次数或总时间限制。传感器断线、Echo 卡高或机械被卡住时，系统可能长期停留在避障循环。

建议增加 Echo 上升沿和下降沿超时、单次测距最大等待时间、连续无效样本计数及安全动作。超过阈值后应停止电机/舵机或回到安全站立状态，并允许串口急停命令优先打断避障流程。

## 性能优化建议

| 优化方向 | 当前实现 | 建议 |
|---|---|---|
| 舵机动作 | 多个动作函数逐舵机调用并配合阻塞延时 | 建立四舵机目标姿态结构体，按固定周期批量更新；减少重复代码并统一动作速度 |
| OLED | 主循环和模式函数中频繁刷新整幅图像 | 仅在表情或状态变化时刷新；对固定图像使用脏矩形更新 |
| 串口发送 | 每个字节轮询等待发送完成 | 使用发送环形缓冲区和 TXE 中断；至少避免在主循环中长时间 busy-wait |
| 浮点运算 | 超声波距离计算使用浮点常量 | 使用整数定点换算，例如按 0.1 mm 或微秒计数，减少 STM32F1 上的浮点开销 |
| 代码体积 | `OLED_Data.c` 和标准外设库包含大量资源 | 在 Keil 中启用函数级链接和死代码消除，并确认未使用字体/图形资源未被链接 |
| 动作可中断性 | 动作函数连续执行数百至数千毫秒 | 使用可取消的动作状态机，让急停、低电量和传感器故障优先级高于普通动作 |

## 建议修复顺序

第一阶段应先修复两个确定的内存/构建问题：删除 ASRPro 的重复 `setup()`/`loop()`，扩大并限制 `read` 缓冲区，同时为 `SYN_FrameInfo` 增加容量检查。第二阶段处理串口环形缓冲区、`volatile` 共享变量、ASR 队列空指针保护和运动命令的非阻塞化。第三阶段再优化超声波测距、OLED 刷新、舵机动作抽象和浮点运算。

本次审查**没有修改或推送上述新增问题的修复**，以避免在未进行硬件验证的情况下改变机器狗动作逻辑。若需要，我可以按上述顺序先修复 P0 项，并创建单独提交供你编译验证。
